# Lantern — Phase 4 Extension Instructions
## General Text and Source Code Support, UTF-8 Normalization

Extend the existing Phase 4 Document Extraction Pipeline to support general text files, source code, configuration files, and consistent UTF-8 output.

This is an extension of Phase 4, not a new implementation phase.

Preserve all existing document extraction, structure-aware chunking, and hybrid search functionality.

## 1. General Text File Support

Expand text extraction beyond TXT and Markdown.

Lantern is a general-purpose full-text search platform and should support arbitrary text-based files, including source code and configuration files.

### Target file types

Support common extensions, including but not limited to:

| Category | Extensions |
|---|---|
| C / C++ | `.c`, `.h`, `.cc`, `.cpp`, `.cxx`, `.hpp`, `.hxx` |
| C# / .NET | `.cs`, `.csproj`, `.fs`, `.fsproj`, `.sln`, `.props`, `.targets` |
| Rust | `.rs`, `.toml` |
| Python | `.py`, `.pyi` |
| Java / Kotlin | `.java`, `.kt`, `.kts` |
| JavaScript / TypeScript | `.js`, `.jsx`, `.ts`, `.tsx`, `.mjs` |
| Web | `.css`, `.scss`, `.json`, `.xml`, `.yaml`, `.yml` |
| Shell / Scripts | `.sh`, `.bash`, `.ps1`, `.bat`, `.cmd` |
| SQL | `.sql` |
| Configuration | `.ini`, `.cfg`, `.conf`, `.properties`, `.env` |
| Documentation | `.txt`, `.md`, `.rst`, `.adoc`, `.tex` |
| Logs / Data | `.log`, `.csv`, `.tsv`, `.jsonl`, `.ndjson` |
| Other | `.gitignore`, `.editorconfig`, `Dockerfile`, `Makefile`, extensionless text files |

The list is not exhaustive.

Avoid implementing a separate extractor for every programming language.

Use a shared general-purpose text extractor.

### Text versus binary detection

Implement a lightweight text/binary classification mechanism.

Do not rely exclusively on file extensions.

Use a bounded content sample and appropriate heuristics to detect likely binary files.

Recognize UTF-16 text without incorrectly classifying it as binary because of null bytes.

Never indiscriminately decode arbitrary binary data as text.

Allow known text extensions and user configuration to influence detection.

Return an explicit unsupported or binary-file result where appropriate.

## 2. Character Encoding Detection and UTF-8 Normalization

All supported text inputs must be converted into a consistent Unicode representation.

### Input encodings

Support at least:

- UTF-8 with BOM.
- UTF-8 without BOM.
- UTF-16 LE.
- UTF-16 BE.
- UTF-32 where practical.
- Common legacy encodings when reliably identifiable or explicitly configured.

For Japanese documents, consider:

- Shift_JIS / Windows-31J.
- EUC-JP.
- ISO-2022-JP.

Do not assume that every file is UTF-8.

### Encoding detection strategy

Use the following precedence:

1. Explicit encoding supplied by the caller or source configuration.
2. Recognized Unicode BOM.
3. Strict UTF-8 validation.
4. Configured or reliably detected legacy encoding.
5. Controlled failure when encoding remains ambiguous.

Do not automatically interpret invalid UTF-8 as Windows-1252 or Shift_JIS without sufficient evidence.

Avoid silent mojibake.

Do not indiscriminately replace invalid byte sequences with Unicode replacement characters.

Expose the detected or selected encoding in extraction metadata.

### Internal representation

Use normal .NET `string` values for decoded text.

Do not attempt to force .NET strings into UTF-8 storage.

Normalize text after successful decoding.

### Output encoding

All byte-oriented textual output produced by the extraction pipeline must use UTF-8.

This includes:

- Serialized JSON.
- Exported extracted text.
- Diagnostic text files where applicable.
- Text fixtures generated by development utilities.

Prefer UTF-8 without BOM for generated files unless a format explicitly requires otherwise.

Do not rewrite or modify original source files.

The extraction pipeline must be read-only.

## 3. Source Code Preservation

Source code requires different normalization rules from ordinary prose.

### Requirements

Preserve:

- Indentation.
- Line breaks.
- Tabs where meaningful.
- Symbols and operators.
- Comments.
- String literals.
- Unicode identifiers.
- Preprocessor directives.
- Code block boundaries.

Do not collapse whitespace within source code.

Do not remove comments.

Do not reformat code.

Do not modify identifiers or normalize punctuation.

### Line numbers

Preserve line location information.

Where practical, record:

```text
StartLine
EndLine
```

for extracted blocks and generated chunks.

These fields should be optional and compatible with the existing structured document model.

Do not fabricate line numbers when accurate mapping is unavailable.

### Chunking

For source code, prefer boundaries such as:

1. Functions or methods when reliably identifiable.
2. Classes or declarations when reliably identifiable.
3. Blank-line-separated logical blocks.
4. Line boundaries.
5. Token limits as a fallback.

Do not introduce full parsers for every programming language.

A lightweight line-aware chunking implementation is sufficient initially.

Avoid splitting individual source lines when possible.

Preserve line-number metadata in the resulting `SearchChunk`.

## 4. Structured Text Formats

Handle JSON, XML, YAML, TOML, INI, and similar formats as searchable text.

Preserve keys, values, nesting indicators, and useful whitespace.

Do not attempt to execute or evaluate configuration files.

Do not interpolate environment variables or resolve external references.

For potentially sensitive configuration files such as `.env`, avoid logging extracted values.

Respect existing crawler source approval and access policies.

Do not automatically exclude all configuration files, but allow administrators to configure exclusions.

## 5. Integration with Existing Pipeline

Reuse the Phase 4 extractor dispatcher.

Introduce or extend a general-purpose text extractor.

Conceptually:

```text
Input File
    |
    v
Text / Binary Classification
    |
    v
Encoding Detection
    |
    v
Unicode Decoding
    |
    v
Text Normalization
    |
    v
Structured Text Blocks
    |
    v
Existing Chunking Pipeline
    |
    v
SearchChunk[]
```

Do not duplicate the existing chunking or indexing infrastructure.

Do not perform UTF-8 conversion inside the embedding server.

The embedding server must continue to receive valid Unicode text through the existing JSON API.

## 6. Tests

Add regression tests covering:

1. UTF-8 with BOM.
2. UTF-8 without BOM.
3. UTF-16 LE and BE.
4. Japanese Shift_JIS text.
5. Japanese EUC-JP text where supported.
6. Invalid UTF-8 sequences.
7. Ambiguous encoding detection.
8. Binary input rejection.
9. Extensionless text files.
10. Source code indentation preservation.
11. C/C++ comments and preprocessor directives.
12. Rust and Python source files.
13. JSON, YAML, XML, and TOML.
14. Line-number preservation.
15. Chunk boundaries for source code.
16. Unicode preservation through chunking.
17. UTF-8 serialization.
18. Original input files remaining unchanged.

Use deterministic fixtures.

Verify that Japanese and English text remain readable and searchable.

Run all existing Phase 4 extraction and chunking tests.

## 7. Scope Restrictions

Do not implement:

- Compiler-based source analysis.
- Language Server Protocol integration.
- AST parsing for every language.
- Repository dependency analysis.
- Syntax highlighting.
- Code execution.
- Automatic source formatting.
- Source file modification.
- OCR.
- A new embedding model.
- A separate source code search engine.

Keep this extension focused on extraction, encoding, metadata, and chunking.

## 8. Acceptance Criteria

The extension is complete when:

- Common programming language files are extractable.
- Configuration files and general text files are supported.
- Extensionless text files can be recognized.
- Binary files are not misclassified indiscriminately.
- Supported input encodings decode correctly.
- Ambiguous encodings produce controlled diagnostics.
- Extracted text is serialized as UTF-8 when written to bytes.
- Source code indentation and line structure are preserved.
- Accurate line metadata is retained where available.
- Existing structure-aware chunking remains functional.
- Existing PDF and Office extraction behavior is preserved.
- Existing keyword and hybrid search functionality is not broken.
- Automated tests pass.

## Final Instructions

Extend the existing Phase 4 implementation rather than rewriting it.

Use one reusable general-purpose text extractor for source code, configuration files, logs, and other text formats.

Treat input encoding detection and decoding as a separate concern from text normalization.

Preserve source code formatting and accurate line information.

Use UTF-8 consistently for byte-oriented textual output.

Do not modify original source files.

Maintain compatibility with the existing Lantern document extraction and hybrid search pipeline.

**The primary success condition is that Lantern can reliably extract and index Japanese and English text from common documents, programming source files, configuration files, and arbitrary text-based files without corrupting encoding, whitespace, or source locations.**
